# ShoppingList — правила для агента

Общие правила разработки пользователя действуют. Ниже правила этого проекта.

## Проект в двух словах
Мобильное приложение «ShoppingList» — список покупок с планированием по дням. Android сначала, iOS потом.
Expo (React Native) + TypeScript + expo-router + expo-sqlite. Всё офлайн, без сервера. Продукт для массового использования.
Инфраструктура перенесена из «Чекпоинта» (`C:\Projects\Checkpoint`). Продукт: `PRODUCT.md`. Эскизы и логотип: `design/`.

## Начало сессии (экономия токенов)
1. Прочитай только: этот файл, `PRODUCT.md` (по разделам) и текущее задание.
2. Не сканируй весь репозиторий. Ищи точечно (Grep/Glob).
3. Никогда не читай: `node_modules/`, `package-lock.json`, `.expo/`, `assets/` (бинарники), `android/`.
4. Цвета и палитры — `src/theme/themes.json` (рабочая копия; `assets/themes.json` — исходник из архива).

## Работа
- Делай только то, что в текущем задании. Идеи — одной строкой в «Идеи» ниже.
- Пакеты — только через `npx expo install <pkg>` и только после «да» пользователя.
- Без эмулятора. Проверка — на телефоне пользователя. `npx expo start` не запускай сам.
- Проверки: `npx tsc --noEmit`, `npx expo lint`, `npm test`.
- ОС: Windows, PowerShell. ОЗУ 8 ГБ.
- Эскизы утверждены: `design/screens.html`. **Любое изменение интерфейса — сначала эскиз и «ок», код только после него.** Даже мелкое (размеры, кнопки, поля, обводка) и даже по просьбе тестировщика. В 0.6.2 окно «Количество» («10», «Своё число») ушло в код без эскиза — больше так не делать.

## Продакшен
1. `tsc`, `lint`, `test` — без ошибок; новая логика покрыта тестами.
2. Тексты — в `src/i18n/` на трёх языках (kk — на проверку носителем).
3. Миграции БД не теряют данные (тест «старая БД → новая»); уже выпущенные шаги не менять.
4. Цвета — только через `useTheme()`; контраст проверяется тестами.
5. Нет пакетов с сетью/аналитикой; зоны нажатия ≥ 48 dp, `accessibilityLabel`.

## Постоянные требования (опыт «Чекпоинта»: APK был 56 МБ)
Сборка APK:
- Только 64 бита (`reactNativeArchitectures=arm64-v8a`), один APK; 32-битную не делаем, пока не понадобится.
- В release сразу R8/minify + shrinkResources; языки ресурсов только ru, kk, en (resConfigs или localeFilters — по версии Gradle); правила keep для своих нативных модулей; после включения проверить на телефоне все функции.
- README репозитория релизов: «нужен 64-битный Android; если пишет "приложение несовместимо" — сообщите».

Архитектура и код с первого этапа:
- Все списки — FlatList/SectionList, не ScrollView.
- Слои экран → logic → db: без SQL и расчётов в экранах; индексы под частые запросы; без «запроса в цикле».
- Ничего лишнего до первого экрана — тяжёлое грузить после.
- Никаких неиспользуемых пакетов; без console.* в release.
- Цвета только из темы, тексты только из i18n.
- Перед этапом первой сборки APK и после каждых 2–3 этапов — проход проверки: агент присылает таблицу «проблема · где · что даст · риск» и правит только одобренное.

Рабочие заметки:
- Gradle в песочнице агента не запускается: APK собирает пользователь (`powershell -ExecutionPolicy Bypass -File scripts\build-apk.ps1`), агент проверяет файл и SHA-256.
- Скрипт сборки сам сохраняет и возвращает `package.json` после prebuild (не использовать `git checkout package.json`: он теряет незакоммиченные пакеты). В PowerShell — `npx.cmd` вместо `npx`.
- Релиз: `gh release create` с APK → `latest.json` → push репозитория APK → тег и push основного; хэш только из файла.
- Канал уведомлений создавать сразу с высокой важностью (потом не повысить).
- Выбор темы — одним списком «Как в системе» + все схемы.

## Код
- Код и имена — на английском, тексты — через i18n.
- Экраны → `src/logic/` → `src/db/`. Экраны не пишут SQL и не считают правила.
- Маленькие файлы: один экран или компонент — один файл.

## Ответы пользователю
До 10 строк, простым языком: что сделано и как проверить.
